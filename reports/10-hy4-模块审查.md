# forge 贡献模块架构审查（只读）

审查范围：`forge/registry.py` + `forge/contrib/` 下 9 个模块（heartbeat / scheduler / replay / router / toolhost / mcp_bridge / curator / teams / compactor）。未执行代码，结论均来自源码静态阅读；无法由代码确认的判断已标（推测）。

先说一个全局事实：除 `forge/selftest.py` 的集成测试外，**`forge/*.py` 中没有任何代码调用 contrib 钩子**（`loop.py:233` 用的是 `memory.py` 自带的 compactor）。也就是说这 9 个模块目前是"装好未接线"的状态，下面大部分冲突是潜伏的，一旦按 `selftest.py:1085` 的接线方式接入主循环就会爆发。

## 1. 逐模块契约遵守情况

### heartbeat.py
- 纯函数，无全局状态。但它是 **capability 重名竞争者**：`heartbeat.py:48` 声明 `schedule.periodic` / `schedule.due-check`，与 `scheduler.py:121-122` 完全同名；而它的 `due()`（29-43）不认 `paused`、不认 lease、不认 gate。
- hook 名为 `on_tick`，**不在 `HOOK_ALIASES`（registry.py:100-124）任何条目中** → 按规范名永远解析不到这个函数。
- 边界：`float(job.get("everySeconds") or 0)`（37）对非数字字符串抛 `ValueError`，与其余模块"绝不抛异常"的口径不一致。

### scheduler.py
- 纯函数。**最大的逻辑洞是伪闸门**：`due_jobs()` 第 47 行每次调用现造 `{"paused": False, "pausedUntil": None}` 传给 `_gate_raw` → 全局暂停分支**恒不阻断**，代码看着检查了，实际永不生效。
- `due_jobs` 完全不看 `leaseOwner` / `leaseExpiresAt` → 已被别的节点租住的任务照样判为到期，与 `acquire_lease` 自相矛盾（重复执行）。
- 到期集无"抑制/改期"通道：`lastRunAt` 缺失或 ≤0 恒为到期（60-62），宿主若不写回 `lastRunAt`，每 tick 都返回同一批任务 → 热循环。
- `import time`（14）未被使用——作者原本想读时钟；registry 并不禁止 `time`（见 §3）。
- 18 条自检里**没有一条覆盖"gate 阻断时 due_jobs 返回空"**，因为那是死代码，测不出来。
- 边界：`paused` 只认 `is True`（58），字符串 `"true"` 不生效；`leaseExpiresAt == now` 视为过期。

### replay.py
- **非纯，有全局副作用**：`selftest()`（739-749）直接替换全局 `sys.stdout`，且只 `except Exception` → 若 `_selftest()` 内抛出 `BaseException`（SystemExit / KeyboardInterrupt），`sys.stdout` 永久留在 StringIO，**宿主进程输出被吞**。`_selftest()` 里的 `sys.stdout.reconfigure(...)`（470-473）同样是对全局对象的写。
- 契约违反：`replay():284-286`、`fork_plan():362-364` 对非法 `until_ordinal` / `keep_last` **抛 TypeError**（含 bool），与模块自述"绝不因数据抛异常"及整体降级风格冲突。
- 逻辑：`_valid_event`（95-111）以"上一个有效事件"为单调基准，一条 ordinal 异常巨大的合法事件会永久抬高基准，后续正常事件全被判 malformed，无重同步/上界机制。
- 一致性：`_clean_events`（253-256）不校验 ordinal → 同一条数据在 `replay` 里被丢弃、在 `diff_runs` 里被采信，两个函数对"合法性"的判定不一致。
- `first_divergence`（432-437）在 a 是 b 的真前缀时取 a 侧下标，语义上应指向 b 的新增事件。

### router.py
- 真纯函数，无全局可变状态，13 条自检，质量最高。
- fail-open：`_judge():122` 只认 `healthy is False` → **缺 healthy 字段的 worker 直接当选**。
- fail-open：`maxCost` 非字符串（如数字 `1`）时直接跳过成本检查（128）→ 绕过成本上限。
- `fallback_plan():214` 声称"上一项失败且属于可重试类才前进"，但签名里没有任何失败信息入参 → 该语义无法实现，`on` 字段是死语义。
- 全局预算耗尽时清空 `order`（186-189），但 `rejected` 仍保留个体淘汰记录，调用方只读 `rejected` 会误判。

### toolhost.py
- 声称纯，实际读进程状态：`_resolve_target():174` 在 workspace 为空时 `os.getcwd()` → 结果依赖 CWD，非纯。
- **P0 权限模型缺陷**：`authorize():219` 用 `_guess_read_only(tool)` **按工具名前缀**判定只读，而 `register_tools` 归一化时算出的权威 `read_only`（尊重 `readOnlyHint`，126-129）**根本没传进 `authorize`**。后果：把破坏性工具命名为 `read_* / list_* / get_* / fetch_* / debug_*` 等 14 个前缀之一，或叫 `tool_search`，即可 (a) 完全跳过沙箱路径检查（225-237 只对非只读工具生效）、(b) 在 default/auto/acceptEdits/plan/dontAsk 下直接 `allow`，不弹窗。工具名由不可信的 MCP server 单方面提供 → 完整权限提升链。
- 顺序缺陷：`ask` 规则（240）在 `bypassPermissions`（244）之前 → bypassPermissions 无法绕过 ask 规则，与 mode 语义矛盾。
- 沙箱用 `abspath + normpath`，**不解析符号链接** → workspace 内指向外部的 symlink 通过（P1）；`workspace=""` 时 `_resolve_target` 回退 cwd（174）而 `_is_inside_workspace(resolved, None)` 抛 TypeError→deny（185），两处空值处理不一致。
- 未知 mode 静默降级为 `default`（210-212）而非 deny → fail-open。
- `_NAME_RE`（26）允许 `.` → 工具名 `..` 合法；无长度上限。

### mcp_bridge.py
- 纯函数。**与 toolhost 各自复制了一份只读启发式**（28-51 vs toolhost 26-63），注释里明说"独立复制" → 两份策略必然漂移，修一处不改另一处。
- **P0 跨模块不兼容**：`discover():182` 把工具名改成 `server/name`，而 toolhost 的 `_NAME_RE` 不接受 `/` → discover 的输出喂给 `register_tools`，**所有工具整批落进 `dropped`**（invalid tool name），MCP 工具集静默清零。
- `plan_servers`：failed + enabled → 无退避、无重试上限地建议 start（115-123）→ 永久失败的 server 无限重启；`enabled` 非 bool 时用 `bool(enabled)`（106-108）→ `"false"` 被解释成 True。
- `discover` 不做重名去重（无 `deduped`）；`plan_servers` 完全不校验 `command`/`args`（（推测）宿主侧也没有白名单，因为仓库里找不到消费 start 名单的代码）。
- `health`：`stale_after=True` 会被当成 1 秒（isinstance(True, int)）。

### curator.py
- 纯函数，24 条自检。
- **自相矛盾**：`review():306` 用常量 `DEFAULT_PROTECTED_CREATORS`，忽略 policy 的 `protectCreatedBy`；`curate():214` 用 policy → 自定义 `protectCreatedBy=[]` 时，review 说"受保护"、curate 照归档。
- `ledger_entry():343-350` 抛 `ValueError`（与"不抛业务异常"的邻居风格相反），且 arrow 解析不校验状态对 → 可以写入 `active->archived` 这类状态机禁止的跳变；`now` 也不校验。
- `_normalize_policy:88` 对 `archive < stale` 只 warning 后继续跑 → "每次只推进一格"在时间维度上被打破。
- 缺 id 时用 `<#index>` 占位（121）→ 输入顺序变化时 id 不稳定，账本 `target` 会串。

### teams.py
- 纯函数，29 条自检。
- **静默丢消息**：唯一目标不健康/超预算时（203-211）返回 `delivered=[]`、`denied=[]`，只进 `skipped`。调用方按模块自述的"denied 非空才算失败"判断会认为投递成功。`@all` 且全员不可用时同样双空。模块开头写着"不丢消息"，实际是丢了不报。
- 无 ACL：任何成员都能 `@all` 广播；防冒充只校验 `sender ∈ members`（165-170），不校验寻址权限。
- `advance()`：建 `status_of` 时重复 id **后者覆盖前者**（231-237），而主循环声称"earlier row wins"（248-251）→ 依赖解析用的是后写的状态，与说明相反。
- 依赖成环 / 依赖未知 id → 任务永久"等待中"，既不 ready 也不 blocked，无告警，`complete` 永远 False；`doing` 状态卡死无超时通道（280-281）。
- `complete` 同时用 `not blocked` 和 `all(status_of == "done")`（285），而 `status_of` 含被判 blocked 的任务，重复 id 时口径不稳。

### compactor.py
- 纯（但 `_copy_message` 是**浅拷贝**，"输入不被修改"只对顶层成立，嵌套 `content` 仍共享引用）。
- **自相矛盾的触发条件**：`should_compact` 第三条"单条消息 > 半预算"（69-74）触发的压缩，`plan` 未必能消除——该消息若落在 `keepTail`（默认 6）之内或被 `pinned`，plan 不会丢它 → `compact` 恒为 True → 反复压缩/无效压缩。`plan` 完全不看 budget（80-114），`dropped_chars` 算了却不回验 → 无收敛保证。
- fail-open：`_norm_budget` 把负数夹成 0（45-46），而 0 在 `should_compact` 中表示"不限制"（60/64/69）→ 配一个非法的 `maxChars=-1` 等于关掉字符上限。
- `merge_summary():128` 的 `[compacted N messages]` 里 N 是**剩余**条数，`plan` 的 `summary_placeholder`（106）用**被丢弃**条数 → 同一句话两个含义，与 replay 的 compaction 事件联动时时间线数字是错的。
- `_content_len`（22-23）对非字符串 content 用 `len(str(content))` → 结构化 content 把 JSON 标点算进字符数，阈值失真。

## 2. 模块之间的语义冲突

**(a) router 选中的 worker ≠ teams 的投递对象——三处不一致**
1. 主键不同：router 产出 `worker["name"]`（router.py:119/183），teams 按 `member["id"]` 寻址（teams.py:69/192）。两者不等时 `deliver` 走 `no such member` → denied，派单直接掉地上。
2. 存活口径不同：router 看 `healthy`（router.py:122，缺字段=健康），teams 看 `alive` 或 `alive==0` 加 spend/budget（teams.py:82-89，缺字段=存活）。同一批 agent 用 `alive: 0` 表示已死时，router 依然选中它、teams 又把它 skip → `delivered` 空、`denied` 空 → **任务被选中却被静默丢弃**。
3. 筛选维度不同：router 用 cost/permission/capabilities，teams 一个都不看 → 路由层筛出的唯一合格者可能在投递层被 budget 二次否决，且否决只落在 `skipped`。

`selftest.py:1157` 那条 `integration:handoff-router-to-team` 之所以能过，是因为测试**手工把 worker.name 与 member.id 对齐成同一个字符串、并给两份 roster 各写各的字段**（selftest.py:1139-1146）。这不是验证接缝，是把接缝藏起来了。

**(b) scheduler 到期集与 compactor 触发条件会互相抵消、也会互相放大**
- 两者互不可见：`due_jobs` 只有时间维度，`should_compact` 只有内容维度，没有任何一方读另一方的输出。
- **抵消方向**：把压缩挂成周期 job，scheduler 判"到期"（`lastRunAt` 缺失时恒到期），compactor 判"在预算内" → 宿主若以 should_compact 为准，job 永不写回 `lastRunAt`，下一 tick 又被判到期 → 每 tick 产生一次"到期但不执行"的空转；宿主若以 due_jobs 为准，则完全绕过预算判定做无意义压缩，且 `plan` 不校验是否真的降到阈值以下。
- **放大方向**：一旦 should_compact 因"单条超大消息 / pinned 消息"恒为 True，而 job 又因 never-run 恒为到期 → 每 tick 压一次、每次都不降低 size → 热循环 + 上下文反复被截断。
- 没有"改期/抑制"通道：lease 是唯一互斥手段，但 `due_jobs` 不过滤 lease，且 `acquire_lease` 是纯函数只返回副本，宿主写回丢失即互斥失效。

**(c) 能力命名空间双轨制**
legacy 模块的能力来自 registry 常量表（registry.py:78-89，如 `route.match` / `session.replay` / `context.compact`），契约模块的能力来自各自 manifest（router 写 `router.match`、replay 写 `replay.timeline`、compactor 写 `context.should_compact`）。按 canonical 名消费 `route.match` / `session.replay` / `context.compact` **全部落空**，只有 curator 恰好对上。`selftest.py:1120` 只断言 `len(caps) >= 10`，量够名不对，掩盖了这个洞。

**(d) heartbeat 与 scheduler 竞争同一 capability**
两者都声明 `schedule.periodic` / `schedule.due-check`。`capabilities()` 按文件名字典序返回 `[heartbeat, scheduler]`，按 `owners[0]` 取实现就拿到 heartbeat 的 `due()` → **paused、lease、gate 全部失效**。

**(e) MCP 链路断在归一这一步**
`mcp_bridge.discover` 的 `server/tool` 前缀与 `toolhost._NAME_RE` 互斥（见 §1），是硬冲突不是风格差异。

**(f) 回放与压缩口径冲突**
replay 的 compaction 事件按 before/after tokens 记录（replay.py:202-205），compactor 的 `merge_summary` 把"压缩了 N 条"写成剩余条数 → 回放时间线上的压缩记录是错的。

## 3. registry.py 一致性闸门的绕过路径

### 静态扫描能被骗过（`_static_checks`，registry.py:471-495）

1. **`os` 不在 `FORBIDDEN_IMPORTS`**，只禁了 6 个 `os.*` 点号写法 → `from os import remove, system, rename, truncate, chmod, mkdir, makedirs, replace, link, symlink, spawnl` 全部通过（`ImportFrom` 只查 root 是否在黑名单，`"os"` 不在）。
2. **`_attr_name`（212-219）只解析以 `Name` 开头的属性链** → `import os as _o; _o.system(...)`（得到 `"_o.system"`）、`Path("x").unlink()`（接收者是 Call，链断在 `"unlink"`）、`getattr(os, "system")(...)`、`(os if flag else sys).system()` 全部绕开 `FORBIDDEN_CALLS`。
3. **黑名单大量漏项**：`open`、`pathlib`、`io`、`tempfile`、`pickle`/`marshal`、`importlib`、`builtins`、`sys`、`signal`、`time`/`datetime`、`random`、`sqlite3`、`asyncio`、`threading`、`glob`，以及 `os.walk/chdir/rename/replace/truncate/chmod/mkdir/symlink/spawn*`。`importlib.import_module("subprocess")` 或 `__import__("socket")` 直接穿透（`compile` 禁了，`__import__`/`importlib` 没禁）。所谓"纯标准库、无网络、无破坏性文件调用"，静态层面只剩对 socket/requests/shutil/subprocess 这几个名字的查杀。
4. **跨模块导入禁令只查 `ImportFrom`（489）** → `import forge.contrib.heartbeat` 通过；更直接的：加载后的模块名是可预测的 `forge_contrib_<stem>`（499），任何模块都能用 `sys.modules["forge_contrib_teams"]` 拿到别人的实现。
5. **载荷可外置**：`discover` 跳过 `_` 开头文件（249）→ 把真实逻辑放 `contrib/_payload.py`，被扫描的文件只留 `from _payload import *` 加 register/selftest 三行 → 静态检查对实际执行的代码零覆盖。
6. **不检查纯度和资源**：`time.time()`、`random`、模块级可变全局、`while True`、内存炸弹都不在扫描范围；`_import` / `_collect_assertions` / `_parse_legacy_test` 全部同步执行且**无超时、无资源上限** → 一个死循环或一次超大分配就能挂死/打爆宿主。
7. **编码分歧**：源码按 `utf-8-sig + errors="replace"` 读出做 AST，而 CPython 导入时按 PEP263 cookie 解码（推测：带 latin-1 cookie 的文件可让"被检查的文本"与"被执行的文本"不一致）。

### 动态加载的盲区

8. `spec.loader.exec_module`（506）以**完整进程权限**执行任意代码：可 monkeypatch `forge.*`、改 `sys.path`、装 atexit、起线程（`threading` 未禁）、改 `sys.modules`。静态闸门在它面前只是建议。
9. 只校验 `register()` 返回值的**形状**（name/version/capabilities），不校验 capabilities 是否真实、hooks 是否就是声明的那批函数、register 是否幂等/无副作用。
10. **加载后不再校验**：`discover` 对已加载 stem 直接跳过（251）→ 磁盘文件被替换也不会重新检查；没有 mtime/哈希记录，`report()` 也不留被校验内容的哈希 → 无审计链。
11. 隔离只是字典过滤：`healthy()` 是唯一闸门，`registry.contributions[name].hooks` 可直接取到被隔离模块的钩子（`ok=False` 拦不住直接访问）。
12. **断言可伪造**：契约路径只数 selftest 返回的元组，作者可硬编码 8 条 `(name, True, "")`；`_expand_from_detail`（427-441）更是从 detail 文本里"解析"断言，打印 8 行 `PASS ...` 即可凑数。

## 4. legacy-script 适配层是否降低了安全水位

**降低了，而且恰好降在两个最关键的模块上。** 具体位置：

1. **证据门槛从 8 条降到 1 条**（registry.py:43 vs 38），降幅 87.5%，且没有替代验证手段——注释里说的"集成方的独立验证器"在仓库里不存在，`selftest.py` 只跑 contrib 自己的自检。
2. **`_parse_legacy_test` 会合成一条 PASS**（424-425）：测试无输出且返回 None/False/0/空列表时，生成 `(name, True, "")`，文本里甚至写着 `self-test produced no output`。失败路径反而更严格（返回非空列表→失败，抛异常→失败）→ 整个闸门退化成"作者的测试有没有崩溃"。
3. **恰好 toolhost（权限闸门）和 mcp_bridge（MCP server 生命周期）走这条路**：toolhost 的 18 条断言、mcp_bridge 的 15 条断言，在 registry 眼里都被压成 1 条合成 PASS → 真实证据量 0；`report()["assertions"]`（568）因此系统性低报。
4. **能力按文件名授予**（78-89 + 371）：文件叫 `toolhost.py` 就自动获得 `tools.authorize`；钩子只查 `callable`，不查签名/行为/纯度。
5. **采纳状态不外露**：`capabilities()` / `hook()` 返回的对象没有 adapter 标记，消费方无法知道自己调的是未验证模块，只有 `report()["adopted"]` 里有。
6. **语义陷阱**：`LEGACY_TEST_ENTRIES` 含 `"selftest"`（91）→ 契约入口名与 legacy 测试入口名撞车。mcp_bridge 因此被钉死：一旦补上 `register()` 就走契约路径，把"失败描述列表"当断言收集 → 0 条 → 被隔离。**想升级反而被降级。**
7. **归因可伪造且平台相关**：`AUTHORS_FILE = "AUTHORS.json"`（93）而实际文件是 `contrib/authors.json`（小写）→ Windows 命中、case-sensitive 文件系统上落空（推测：Linux 上全部变 `(unattributed)`）；且 manifest 与 authors.json 互相矛盾（replay 的 manifest 写 `stepclaw`、authors.json 给 `zcode`；router 自称 `ZCode` 却不在表里）→ 追责链断。
8. **判定依赖英文关键字**：`_parse_verdict_lines`（443-458）只认 `pass/[pass]/✅/✓/✔` 与 `fail/[fail]/❌/✗/×`。replay 全靠打印 `PASS 自检 N` 才凑够 18 条；作者改成"通过"就会因"断言不足 8 条"被隔离，反之打印 8 行以 pass 开头的文本即可伪造。把代码正确性绑在输出文案上是脆弱耦合。
9. **别名表与运行时脱节**：`implementation()`（184-194）解析别名，但 `hook()`（540-547）不走别名表；`implementation()` 每次调用还 append 一条 warning → 命名漂移只在自检里被记录，运行时要么取不到、要么静默取到错误的提供者（见 §2d）。
