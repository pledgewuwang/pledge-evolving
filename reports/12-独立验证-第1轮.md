## 1. 数字账：对得上，但账本里有两行空行

自检与模块闸门的账都核过：`selftest` 228/228、退出码 0；`modules validate` 11/11 健康、164 条断言、30 个能力标签、29 个钩子不可达 0。README 与 PLAN 里写的数字与实测一致。**这一层没有问题。**

问题在第 2 组：164 条断言里，有 2 条不含任何可核验内容：

```
mcp_bridge::legacy:selftest: self-test produced no output
toolhost::legacy:_self_test: self-test produced no output
```

出处是 `forge/registry.py` 的 `_parse_legacy_test()`（L420-447）。它的判定链是：

1. 跑作者的测试入口，捕获 stdout；
2. 若返回值是非空 list/tuple → 解析成断言行；
3. 否则按行首标记（pass/fail）解析 stdout；
4. **若一行都没解析出来 → 直接补一行 `(f"legacy:{entry}: {label}", True, "")` —— 判 pass**（L442-445）。

于是"这位贡献者的测试跑完什么都没说"和"这位贡献者交了 10 条全过的测试"在账本上长得一样。`ADAPTER_MIN_ASSERTIONS = 1`（L43）让这一行**足以满足入库门槛**。

## 2. 闸门对抗：空自检和真自检，闸门给的判决一字不差

第 2 组说明的是"账本里有空行"，第 3 组说明的是"空行会导致什么"。做法是在 `tempfile` 副本里做两个对照实验（不动真代码）：

| 实验 | 改动 | 预期 | 实测 |
| --- | --- | --- | --- |
| 负对照 | 把 `toolhost._self_test` 整体替换为 `return []`（删掉全部 10+ 条检查） | 闸门应拦 | **healthy=11、assertions=164，与基线完全一致，toolhost 照常入库** |
| 正对照 | 把 `_guess_read_only` 改成恒返回 `True`（破坏一处真实行为） | 闸门应拦 | **healthy=10，toolhost 被隔离，隔离理由"contributor self-test failures: 只读启发失败, 越界路径被拒失败…"** |

正对照证明了这套闸门**有能力**拦住坏实现——作者的测试是真的、会响。所以问题不是"测试是假的"，而是：

> **闸门无法区分「测试跑过并通过」与「测试不存在」。**

这两件事在判决上等价，于是 `ADAPTER_MIN_ASSERTIONS = 1` 这条底线可以被一行空输出顶掉。任何一份贡献模块只要删掉自己测试的函数体，就能以同样的姿态入库。

**一个必须点明的连带影响**：`_parse_legacy_test` 对"返回值是非空列表"和"stdout 有标记行"两条路径都解析得不错，唯独"全过且静默"这条路径兜成了 pass。toolhost / mcp_bridge 采用的正是"失败才返回"的写法，所以它们两份的通过证据全部落进了这条兜底路径。

## 3. 接缝断裂：mcp_bridge 的产物，toolhost 收不了

第 4 组。两个模块**各自的自检都过**，但它们之间的数据契约对不上：

```
mcp_bridge.discover({"name": "fs"}, [{"name": "read_file"}])   →  "fs/read_file"
toolhost.register_tools([{"name": "fs/read_file"}])            →  保留 []，丢弃 ["invalid tool name: 'fs/read_file'"]
```

而且这不是"两个模块用了两套规范"，是**同一个模块自相矛盾**：

- `mcp_bridge.py` L28：`_NAME_RE = re.compile(r"^[A-Za-z0-9_.\-]+$")` —— 用来校验**入参**名字；
- `mcp_bridge.py` L182：`final_name = f"{server_name}/{name}"` —— 生成**出参**名字，带 `/`；
- 于是 `mcp_bridge._is_valid_name("fs/read_file")` 返回 **False**：它产出自己语法不接受的字符串。

`toolhost.py` L26 用的是**一模一样的**正则。所以真实链路上，凡带 server 前缀的 MCP 工具 = **全部被丢弃**；即便不被丢弃，`_guess_read_only("fs/read_file")` 也不再命中 `read*` 前缀，只读工具会被判成写工具（探针 C 行：`fs/read_file -> deny, write tool with no provably sandboxed target path`）。

**根因不是谁写错了代码**：两份任务书都没冻结工具名的 grammar —— `briefs-round3.md` 一边要求"跨 server 同名时加前缀 `server/tool`"，一边要求名字满足那个不含 `/` 的白名单。同一份任务书里两条要求互斥，而这两份模块恰好出自同一位贡献者（`authors.json`：`toolhost` ← Trae、`mcp_bridge` ← Trae）。

## 4. 命名即权限：read-only 模式下，名叫 `read_*` 的写工具被放行

第 5 组，也就是审查报告标为 P0 的"命名即权限"。`toolhost.authorize()`（L193）的形参是 `(tool, mode, rules, target_path, workspace)` —— **它拿不到工具的声明，只能拿名字**。而是否走沙箱检查，取决于 `_guess_read_only(tool)`（L57，纯名字前缀启发）：

```
mode = read-only（最严档）
read_secrets   -> allow   "read-only mode allows read tool"
list_and_wipe  -> allow   "read-only mode allows read tool"
delete_file    -> deny    "write tool with no provably sandboxed target path"
write_file     -> deny    "write tool with no provably sandboxed target path"
```

**名字是唯一变量，判决跟着名字翻转。** 一个被攻陷的 MCP server、或一个命名不当的自研工具，只要叫 `read_*` / `list_*`，就绕过了路径沙箱这一整层。

而最讽刺的是：**权威信号本来就在**。`register_tools`（L126-127）已经正确采信了 `readOnlyHint`：

```
register_tools([{"name": "read_secrets", "readOnlyHint": False}]) -> read_only=False   ✓
同一次声明的 authorize("read_secrets", "read-only", ...)        -> allow              ✗
```

归一产物里明明带着 `read_only`，`authorize` 却没有这个入口（探针 E 行）。**这是管道没接上，不是能力缺失。**

## 5. 修复方案（未落地，供集成者裁决）

我**没有**改 `forge/` 下任何文件。原因是其中两条会立刻改变入库结论（把 healthy 从 11 打成 9），属于集成者的决策范围。方案按"最小改动 + 不破坏现有语义"排序：

**P0-A｜堵住空输出兜底（`registry.py`）**

`_parse_legacy_test()` L442-445：解析不出任何 verdict 行时**不要补 pass**。改为返回 0 条断言并记 `problems`（例如 `"self-test produced no verdict rows"`）。这样 `ADAPTER_MIN_ASSERTIONS = 1` 就不再能被空输出顶掉。
连带：`toolhost` / `mcp_bridge` 会当场被隔离 → 必须同时做 P0-B。

**P0-B｜让两份 legacy 模块交出行级证据（`contrib/toolhost.py`、`contrib/mcp_bridge.py`）**

两份的测试都已是"逐条 conditional → 收集失败消息"的形状，改造是把追加失败消息换成追加 `(case_name, ok, detail)` 全量行，**不改任何被测逻辑**。toolhost 的 `_self_test` 里每个 `if ...: failures.append("只读启发失败")` 等价于一行断言，机械转换即可；正对照实验已经证明这些 case 是有效的。
产出效果：assertions 从 164 升到 190+，且每一行都有可核验内容。

**P0-C｜冻结工具名 grammar（`CONTRACT.md`）**

把命名规范从"两边各自猜"改成契约里写明的一条。二选一，**必须只选一个**：
- 命名空间用 `/`，则 toolhost 的 `_NAME_RE` 放宽为 `^[A-Za-z0-9_.\-]+(/[A-Za-z0-9_.\-]+)*$`；
- 命名空间用保留分隔符 `__`，则 mcp_bridge 的 `f"{server}/{name}"` 改为 `f"{server}__{name}"`，两个模块的现有正则都不用动（**成本最低**）。
无论选哪个，`_guess_read_only` 都要先把命名空间前缀剥掉再判前缀，否则只读启发在带前缀的名字上永久失效。

**P1-D｜把 `read_only` 接进裁决（`toolhost.authorize` 加形参）**

`authorize(tool, mode, rules, target_path, workspace, spec=None)`：`spec` 可传归一产物；有 `spec["read_only"]` 时**以声明为准**，名字启发只作无声明时的兜底，且兜底要落一条 warning 事件。这是接口变更，按集成者的意见放进 v4 契约变更统一做更稳妥；但**在改动之前，"名字即权限"应当作为一个已知漏洞记在 README 的"已知边界"里**，不能继续以"三档沙箱 + 黑名单"的宣传口径出现。

**P0-E｜把对抗实验纳入常规验证（已完成）**

`verify/independent_audit.py` 已落地并跑通，第 3 组的正/负对照可直接作为"闸门是否还有判断力"的回归项。建议每个里程碑跑一次，而不是只在出事后跑。
